# 運用設計（第3段階・最終版）

## 1. 文書の目的
本書は ShizuKa デモ環境の運用方針を明文化し、障害時の初動とデータ保全を標準化するためのドキュメントです。デモ段階として、無料枠または低コストで実行可能な範囲に限定します。

## 2. 前提
- 対象はデモ環境です。
- 本番相当のエンタープライズ監視はまだ導入しません。
- 監視は無料枠を中心に設計します。
- DB は Render のマネージドDBを想定します。

## 3. 現在採用する運用方針
- 監視ツールは無料枠で導入可能なものを使います。
- 現在の採用は UptimeRobot を想定します。
- 高度な観測基盤（例: Better Stack）は将来の拡張候補として位置付けます。
- 予約停止時は管理画面で枠を閉じ、静的サイトで告知します。

## 4. 監視設計
**現在の監視（デモ段階で実施）**
- UptimeRobot による HTTP 監視
- 対象エンドポイント
  - `GET /health`
  - `GET /api/plans`
- 監視間隔は 1〜5 分を目安に設定

**将来の拡張（未実装）**
- 予約作成の合成監視
  - `POST /api/reservations`
- 管理ログインの合成監視
  - `POST /api/admin/auth/login`
  - `GET /api/admin/reservations`
- Better Stack などの観測基盤の導入
  - これは将来のスケールに備えた選択肢であり、現時点の採用ではありません。

## 5. 通知設計
**現在の通知（デモ段階で実施）**
- Slack 通知: `#shizuka-ops-alerts`
- メール通知: `shizuka-ops@...` または運用共有アドレス（確定次第更新）

**将来の拡張（未実装）**
- 重大度レベル別の通知ルール分岐
- 夜間・休日の当番通知設定

## 6. 障害時対応フロー
1. 監視通知を確認
2. `/health` と `/api/plans` の疎通を確認
3. Render ダッシュボードで DB 状態を確認
4. 30 分以内に復旧できない場合は予約停止措置を実施
5. 復旧後、告知解除と再監視確認を行う

## 7. 予約停止時の告知
告知のON/OFFと文言は `repo-root/site/assets/js/ops-config.js` の `reservationStop` と `reservationStopMessage` で切り替える。
**告知の適用先**
- 静的サイトに告知を掲載
- 管理画面内での補助的な告知（任意）

**静的サイトの掲載ページ（確定）**
- `repo-root/site/index.html`
- `repo-root/site/reserve.html`
- `repo-root/site/reserve-select-course.html`
- `repo-root/site/reserve-select-slot.html`
- `repo-root/site/reserve-form.html`
- `repo-root/site/reserve-confirm.html`
- `repo-root/site/reserve-complete.html`

**固定メッセージ（必ず使用）**
現在、システム調整のためオンライン予約を一時停止しております。
再開まで今しばらくお待ちください。
お急ぎのお客様は店舗へ直接お問い合わせください。

## 8. バックアップ / 復旧方針
**現在の方針（デモ段階の運用ポリシー）**
- Render のバックアップ機能が利用可能な場合はそれを活用する
- 自動化が未整備の場合は手動スナップショットまたはエクスポートを実施する
- バックアップは日次を目標とするが、現時点は運用ポリシーとして記載する

**復旧の考え方**
- 重大障害時は直近のバックアップからのリストアを検討
- 復旧手順は月1回の確認を目標とする（まだ自動化されていない）

- エラーレート監視とパフォーマンス監視
